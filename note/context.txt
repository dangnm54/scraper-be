Project Goals
You are building an automated web scraper for Airbnb to perform live market research. The core purpose is to collect publicly available data and display it on a dashboard. Your long-term goal is to build a program on top of other AI models, but the immediate focus is on scraping and data analysis.

Project Roadmap
The project follows a phased approach:

Python Foundations: Completed. You have a solid grasp of Python, Pandas, and basic data visualization.

Web Scraping: Current focus. You are learning to use Selenium for controlling a web browser like a human, and BeautifulSoup for parsing web page structures. This phase will cover handling pagination, proxy servers, and robust error handling.

Web Application Development: This will follow the scraping phase. Your goal is to build a web-based user interface using React, Shadcn/ui, and Lucide icons to interact with the Python backend.

AI Integration: This is a later phase, after the core scraping and data handling are complete.

Technical Implementation
The project is split into two main parts: a backend (scraper-be) and a frontend (scraper-fe).

The backend is the "engine" written in Python with FastAPI, responsible for the scraping logic and saving data to a database. It uses Selenium to navigate the Airbnb website and BeautifulSoup to extract data. It will also use proxies to avoid detection.

The frontend is the user interface, built with React and TypeScript, styled with Tailwind CSS. It communicates with the backend via API calls to trigger scraping and display the results.

Specific Scraping Goals
Scrape a list of properties: Use search filters to find properties and collect key details like title, price, rating, and the link to the property detail page.

The project is being developed using an MVP (Minimum Viable Product) approach. This means the immediate goal is to launch the simplest, most basic version of the app to get user feedback as quickly as possible. To achieve this, several features are being intentionally excluded from the initial release:

Authentication: The MVP will not have a user login system or a secure API. The focus is on functionality, not security.

Complex Deployment: The project will use a lean deployment strategy with Railway for the backend and Vercel for the frontend to get the app live quickly, without the need for manual configuration or complex DevOps.

This adjusted, lean roadmap prioritizes getting a working product to market faster.

# Batch Processing Implementation Recap - Approach 1

## **Goal**
Enable FE to send multiple scraping requirements to BE. BE processes them sequentially in the background while FE can close the browser. BE continues scraping uninterrupted.

---

## **High-Level Flow**

1. **FE** sends an array of scraping requirements to new endpoint `/api/run-batch`
2. **BE** receives request → creates batch job in database → returns batch ID immediately
3. **BE** processes requirements sequentially in background using FastAPI's `BackgroundTasks`
4. **User** can close browser - BE keeps processing
5. **FE** can optionally poll `/api/batch-status/{batch_id}` to check progress
6. Each completed job saves results to existing database structure

---

## **Backend Changes Required**

### **1. New Database Model (in `src/type/data.py`)**
Create a `BatchJobDB` SQLAlchemy model:
- `batch_id` (primary key, UUID)
- `created_at` (timestamp)
- `status` (enum: "pending", "processing", "completed", "failed")
- `total_items` (int)
- `completed_items` (int)
- `current_item_index` (int or null)
- `requirements` (JSON field - stores array of scraping configs)
- `error_message` (text, nullable)

### **2. New Pydantic Models (in `src/type/api.py`)**
- `BatchScraperSettings`: Contains `List[ScraperSettings]`
- `BatchJobStatus`: Response model with batch metadata + progress
- `BatchJobMetadata`: For listing all batches

### **3. New API Endpoints (in `app.py`)**

**POST `/api/run-batch`**
- Input: `BatchScraperSettings` (array of requirements)
- Creates batch record in database with status "pending"
- Calls `BackgroundTasks.add_task()` to run batch processor
- Returns batch ID immediately (200 OK)

**GET `/api/batch-status/{batch_id}`**
- Returns current status of batch job
- Includes: total items, completed items, current processing item, status

**GET `/api/batch-list`** (optional)
- Returns list of all batch jobs with metadata
- Similar to existing `/api/data/file-list`

### **4. Background Processing Function (new file: `src/batch_processor.py` or in `app.py`)**
Function: `process_batch_in_background(batch_id, db_session)`
- Fetches batch record from database
- Updates status to "processing"
- Loops through each requirement in the array:
  - Updates `current_item_index` in database
  - Calls existing `run_full_flow()` with that requirement
  - Increments `completed_items` after each finishes
  - Handles errors gracefully (log and continue to next)
- Updates status to "completed" when done
- Logs entire batch completion

### **5. Database Operations (in `src/tool/db_op.py` or `src/tool/file_op.py`)**
Add helper functions:
- `create_batch_job(requirements_list, db)` → returns batch_id
- `get_batch_status(batch_id, db)` → returns BatchJobStatus
- `update_batch_progress(batch_id, completed_count, current_index, db)`
- `update_batch_status(batch_id, status, db)`
- `get_all_batches(db)` → returns list of batch metadata

---

## **Frontend Changes Required**

### **1. Form Modification (in `src/components/main/form-tab/config-form.tsx`)**
- Add UI to collect multiple requirements (e.g., repeat form fields or array input)
- Option 1: "Add Another" button to duplicate form fields
- Option 2: Upload CSV/JSON with multiple configs
- Collect all requirements into array

### **2. API Call Change**
- Modify form submission to call `/api/run-batch` instead of `/api/run`
- Send: `{ requirements: [req1, req2, req3, ...] }`
- Receive: `{ batch_id: "uuid-xxx", message: "Batch started" }`

### **3. Status Polling (optional - in `src/components/main/form-tab/` or new component)**
- Create component that polls `/api/batch-status/{batch_id}` every 5-10 seconds
- Display: "Processing 3/10 requirements..."
- Show progress bar
- User can navigate away - just informational

---

## **Key Technical Details**

**FastAPI BackgroundTasks:**
```python
from fastapi import BackgroundTasks

@app.post("/api/run-batch")
async def run_batch_api(
    fe_input: BatchScraperSettings,
    background_tasks: BackgroundTasks,
    db: Session = Depends(get_db)
):
    # Create batch record
    batch_id = create_batch_job(fe_input.requirements, db)
    
    # Add to background
    background_tasks.add_task(process_batch_in_background, batch_id, db)
    
    # Return immediately
    return {"batch_id": batch_id}
```

**Database Session Handling:**
- Background tasks need their own DB session (don't reuse request session)
- Create new session inside `process_batch_in_background()`

**Existing Logic Reuse:**
- Call existing `run_full_flow()` for each requirement
- Each requirement creates separate files in existing property tables
- No changes to existing scraping logic needed

---

## **Migration Path (Preserve Existing)**

- Keep existing `/api/run` endpoint for single-job requests (backward compatible)
- Batch endpoint is additive, not replacement
- FE can choose single or batch mode

---

## **Testing Strategy**

1. Create batch with 2-3 small requirements
2. Submit batch, immediately close browser
3. Check Railway logs - confirm processing continues
4. Poll status endpoint - verify progress updates
5. Check database - confirm all results saved

---

## **What NOT to Build (Keep Lean)**

- ❌ Job cancellation (user can't stop batch mid-process)
- ❌ Job scheduling (no cron/delayed start)
- ❌ Parallel processing (sequential only for MVP)
- ❌ Retry logic (failed items just skip)
- ❌ Real-time SSE logs for batch (existing SSE is single-job only)
